# Mapa de Suprimentos

No projeto, acesse **Planejamento → Mapa de Suprimentos**. Expanda os grupos da EAP e use **Adicionar insumo** em uma atividade sem subdivisões para planejar um material, insumo ou equipamento. Registros antigos em atividades que se tornaram agrupadoras continuam disponíveis. A data necessária acompanha o início da atividade até ser ajustada manualmente. O botão de sugestão de solicitação usa os dias úteis do cronograma e explicita quando substituirá uma data preenchida.

Para encaminhar a Compras, informe em cada linha a quantidade a solicitar ou use **Selecionar quantidade restante**, depois escolha **Encaminhar selecionados para Compras**. Confira antes o estoque apresentado: ele é informativo e não é reservado pelo mapa. O sistema cria uma requisição no fluxo já existente. Itens do mesmo cadastro, unidade, descrição, datas, prazo, observações e tipo são consolidados; cada atividade conserva seu vínculo. Equipamento próprio não é encaminhado para compra. Uma necessidade vinculada não pode ser removida nem ter sua identidade alterada; quantidades, custos e datas podem ser ajustados respeitando o que já foi encaminhado.

Novas requisições do mapa recebem um código curto no formato `MAP-AAAAMMDD-NÚMERO`, baseado no identificador da requisição. Códigos antigos compridos continuam armazenados sem alterações e são apresentados no mesmo formato curto nas telas; a busca aceita tanto a apresentação curta quanto o código original.

O consumo usa aplicações de estoque identificadas por projeto, atividade, insumo e unidade, somente quando uma única necessidade histórica corresponde a essa combinação. Ausência de apontamento ou ambiguidade aparece como indisponível. Recebimentos de itens consolidados não são atribuídos automaticamente a cada atividade; preços de compra não são apresentados como custo de consumo. Por isso, o desvio financeiro permanece indisponível enquanto não houver fonte de custo de consumo rastreável. O mapa não altera progresso físico, Curva S, saldos ou reservas.

As migrations `000029`, `000030` e `000031` são aditivas e seguem o mecanismo de migração do projeto. A autorização usa os perfis da EAP para consulta, perfis gestores para edição e a permissão existente de criação de requisições para o encaminhamento. O backend também verifica o tenant e o vínculo com a obra; as tabelas novas usam RLS.

Para executar os testes específicos com PostgreSQL local, configure o ambiente do backend e rode `node tests/mapaSuprimentosValidation.test.js`, `node tests/mapaSuprimentosDatabase.test.js`, `node tests/mapaSuprimentosIntegration.test.js`, `node tests/mapaSuprimentosRls.test.js` e `node tests/mapaSuprimentosConcurrency.test.js`. Os testes de banco usam tabelas temporárias ou um schema de teste exclusivo removido ao final. O teste de RLS exige um papel de aplicação sem BYPASSRLS e pelo menos um vínculo ativo de usuário e tenant.
